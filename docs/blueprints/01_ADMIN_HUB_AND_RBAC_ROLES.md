# Blueprint 01: Административно Табло и Йерархия на Ролите (Admin Hub & RBAC)

## 1. Концепция и Бизнес Стойност
Този модул дефинира централния входен център за управление на приложението (`AdminDashboard`) и строгата **5-нивова йерархия на правата (Role-Based Access Control — RBAC)** с числови тегла.
Вместо прости булеви флагове (`isAdmin: true/false`), системата използва **рангова тежест**, която гарантира, че:
- По-нисък ранг никога не може да редактира, деактивира или изтрива потребител или съдържание на по-висок ранг.
- Всеки административен модул се показва или скрива динамично според ролята на текущия потребител.
- Има вграден механизъм за първоначално придобиване на роля `OWNER` (`Claim Ownership`) при първи деплой на нов проект.

## 2. Абстрактна Схема на Данните и Константи на Ролите

### Дефиниция на ролите и числовите тегла (`src/constants/roles.js`)
```javascript
export const ROLES = {
  OWNER: 'owner',         // Пълен контрол, Одит лог, Изтриване завинаги, Облачни архиви
  ADMIN: 'admin',         // Управление на данни, реклами, потребители (без Owner) и AI конфигурация
  MODERATOR: 'moderator', // Модерация на съдържание/общност, Събития, Потребители (само за четене)
  USER: 'user',           // Регистриран потребител със собствено съдържание
  GUEST: 'guest'          // Неавтентикиран посетител
};

export const ROLE_HIERARCHY = {
  [ROLES.OWNER]: 4,
  [ROLES.ADMIN]: 3,
  [ROLES.MODERATOR]: 2,
  [ROLES.USER]: 1,
  [ROLES.GUEST]: 0
};
```

### Универсални помощни функции за проверка на ранг
```javascript
export const getRoleWeight = (role) => {
  if (!role) return 0;
  const normalized = String(role).toLowerCase().trim();
  return ROLE_HIERARCHY[normalized] ?? 1;
};

// Проверява дали извършителят има строго по-висок ранг от целевия потребител
export const hasHigherRole = (actorRole, targetRole) => {
  return getRoleWeight(actorRole) > getRoleWeight(targetRole);
};

// Проверява дали потребител има право да изтрие чужд обект/коментар/публикация
export const canDeleteContentByRank = ({ actorId, actorRole, authorId, authorRole }) => {
  if (!actorId) return false;
  if (actorId && authorId && String(actorId) === String(authorId)) return true; // Собствено съдържание
  return hasHigherRole(actorRole, authorRole || ROLES.USER);
};
```

| :--- | :--- | :---: | :---: | :---: | :--- |
| **Модерация** | `/admin/moderation` | ✅ | ✅ | ✅ | Жив брояч на чакащи записи + сигнали от общността |
| **Потребители** | `/admin/users` | 👁️ (Read-Only) | ✅ | ✅ | Админ не може да пипа `OWNER`; Модератор само преглежда |

| **Бекъп и Сигурност** | `/admin/backup` | ❌ | ✅ | ✅ | Облачни бекъпи, JSON експорт/възстановяване и AI Мигратор |

| **Събития / Каталог** | `/admin/events` | ✅ | ✅ | ✅ | Пълен CRUD за оторизирани роли |

## 4. Бизнес Логика и UX Потоци

### 4.1. Жив комбиниран брояч върху картата „Модерация“
В `AdminDashboard` се поддържат два реалновремеви слушателя (`onSnapshot`):
1. Слушател за нови/редактирани обекти в базата със `status == 'pending'`.
2. Слушател за докладвани сигнали от общността в `campaigns/community_reports`, филтриращ сигналите със `status === 'pending'`.
Сумата `pendingCount = pendingEntitiesCount + pendingReportsCount` се визуализира като контрастен червен бадж в горния десен ъгъл на картата „Модерация“.

### 4.2. Бутон за Първоначално Придобиване на Собственост (`Claim Ownership`)
При стартиране на нов проект базата данни няма назначен `OWNER`.
- Ако текущо вписаният потребител има имейл, съвпадащ със зададения главен имейл на създателя, и текущата му роля все още не е `OWNER`, на най-горна позиция в `/admin` се показва специален златен бутон **„Придобий права на Собственик (Owner)“**.
- При натискане и потвърждение полето `status.level` в `users/{uid}` се обновява на `owner`, действието се записва в `activity_logs` и след презареждане бутонът автоматично се скрива.

### 4.3. Защита на маршрутите (`ProtectedRoute`)
Всеки административен маршрут е обвит в `<ProtectedRoute allowedRoles={[...]} />`, който проверява:
1. Дали автентикацията е приключила (`loading === false`).
2. Дали потребителят е активен (`status.is_active !== false && status.is_deleted !== true`).
3. Дали ролята му присъства в `allowedRoles`. При липса на права показва локализиран екран за ограничен достъп с бутон за връщане.

## 5. Готов Промпт за AI Агент (Copy-Paste за нов проект)

```markdown
Искам да имплементираш Административен Контролен Център (`AdminDashboard`) и 5-нивова система за роли и права (RBAC) със следната архитектура:

1. Дефинирай константи `ROLES` (`owner`, `admin`, `moderator`, `user`, `guest`) и числови тегла `ROLE_HIERARCHY` (`owner: 4`, `admin: 3`, `moderator: 2`, `user: 1`, `guest: 0`).
2. Създай помощни функции `getRoleWeight(role)`, `hasHigherRole(actorRole, targetRole)` и `canDeleteContentByRank({ actorId, actorRole, authorId, authorRole })`, така че изтриване на чуждо съдържание да е позволено само на потребител със строго по-висок ранг от автора.
3. Изгради `AdminDashboard` (`/admin`) с карти за навигация към:
   - Модерация (`/admin/moderation`) — видима за Owner, Admin, Moderator, с жив `onSnapshot` бадж за общия брой чакащи записи и докладвани сигнали.

   - Дневник на действията (`/admin/activity`) — видим САМО за Owner.
   - Бекъп и Сигурност (`/admin/backup`) — видим за Owner и Admin.
   - Реклами и Кампании (`/admin/ads`) — видим за Owner и Admin.
   - AI Конфигурация (`/admin/ai-config`) — видим за Owner и Admin.
4. Добави защитен бутон `Claim Ownership` в `/admin`, който се показва само за предварително конфигурирания имейл на собственика, ако ролята му все още не е `owner`.
```
